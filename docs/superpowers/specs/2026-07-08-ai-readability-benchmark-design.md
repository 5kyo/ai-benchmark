# AI 친화도 벤치마크 대시보드 — 설계 문서

- **작성일**: 2026-07-08
- **상태**: 설계 확정 (구현 계획 대기)
- **목적 요약**: 국내 블록체인 기업 공식 홈페이지가 "AI/AI Agent가 읽기 좋은가"를 다각도로 분석·점수화하고, 우리 회사 홈페이지를 AI 친화적으로 개선할 근거와 방향을 제공하는 벤치마크 대시보드.

---

## 1. 배경 & 목표

### 1.1 한 줄 정의
국내 블록체인 관련 기업 공식 홈페이지를 대상으로, AI/AI Agent의 **읽기 용이성**과 **데이터 품질**을 여러 관점에서 분석·점수화하여 순위·비교·개선점을 보여주는 웹 대시보드.

### 1.2 핵심 목적 (우선순위 순)
1. **우리 회사 홈페이지 개선**: AI Agent가 읽기 좋은 공식 홈페이지로 만들기 위한 진단·개선 항목 도출. (최우선)
2. **경쟁사 대비 벤치마크**: 우리 회사 + 경쟁사를 나란히 비교해 개선 우선순위 판단.
3. **모델 간 인사이트**: 같은 사이트를 Claude와 GPT가 얼마나 다르게 읽는지 자체를 관찰.

### 1.3 주 사용자
기술 벤치마크/개선 목적의 내부 사용자(본인 및 팀). 대외 공개 리서치가 1차 목적은 아님.

### 1.4 성공 기준
- 우리 회사 + 경쟁사 20~50개가 동일 기준으로 채점되어 순위·비교로 보인다.
- 각 기업 상세에서 감점 사유와 **구체적 개선 체크리스트**가 나온다.
- 채점 기준(지표·가중치·루브릭)이 웹사이트에 투명하게 공개된다.
- Claude / GPT 모델별 점수를 분리 및 평균 두 방식으로 볼 수 있다.

## 2. 핵심 설계 결정 (확정)

| 항목 | 결정 |
|---|---|
| 평가 대상 | 국내 블록체인 기업 공식 홈페이지, 우리 회사 + 경쟁사 |
| 초기 규모 | 중규모 20~50개 (`companies.yaml`로 관리) |
| 평가 관점(축) | 4개: 크롤링/접근성, 구조화/시맨틱, 콘텐츠 품질, 응답성/기술위생 |
| 채점 방식 | **하이브리드** — 규칙 기반(객관 지표) + LLM 기반(주관 지표) |
| LLM 채점 실행 | **로컬 배치**. 앱 런타임에서 API 호출 안 함. Claude = Claude Code, GPT = Codex CLI |
| 모델 구분 | 모든 LLM 점수는 `model` 필드로 구분. 대시보드는 **모델 평균 뷰 + 모델별 분리 뷰** 모두 제공 |
| 데이터 수집 시점 | **사전 배치 분석**. 결과를 DB에 저장, 대시보드는 저장값을 조회. 주기적(주/월) 재분석 |
| 기술 스택 | Next.js(대시보드) + Supabase/Postgres(저장) + Node/TS 크롤러·스코어링 스크립트 |
| 저장소 구조 | **모노레포** |
| 채점 기준 공개 | 대시보드에 **Methodology 페이지** 포함, `weights.yaml`·루브릭을 그대로 읽어 렌더 |

## 3. 아키텍처 & 데이터 흐름

```
[1] config/companies.yaml  (20~50개 기업 URL·메타)
        │  배치 실행 (주/월 주기, 수동 트리거)
        ▼
[2] 크롤러 (Node/TS)
     · robots.txt / sitemap.xml / llms.txt 수집
     · 페이지 HTML·렌더링결과·응답시간·헤더 저장 → raw/
        │                                   │
        ▼ (자동)                             ▼ (원문 텍스트 추출)
[3a] 규칙 기반 채점기                 [3b] LLM 채점 — 모델별 배치 (로컬)
   · JSON-LD/스키마 검출                ┌ Claude (Claude Code) → JSON (model=claude-*)
   · SSR vs JS, 메타태그                └ GPT (Codex CLI)      → JSON (model=gpt-*)
   · 속도·HTTPS·모바일 등                동일 루브릭·동일 원문 입력, 동일 출력 스키마
   → 객관 지표(JSON, model=rule-based)
        │                                   │
        └──────────────┬────────────────────┘
                       ▼  import 스크립트
[4] Supabase (Postgres): companies / scans / metric_scores / improvements
                       ▼  읽기
[5] Next.js 대시보드: 순위 · 기업상세 · 우리회사vs경쟁사 · 모델비교 · Methodology
```

**중요 원칙**
- **3b는 앱 런타임이 아닌 개발자 배치**: 크롤러/`prepare` 스크립트가 "채점 대기 목록 + 루브릭"을 표준 입력 파일로 만들면, Claude Code·Codex CLI가 그걸 읽고 표준 JSON 스키마로 점수를 출력. 사람 개입은 "배치를 돌린다"뿐, 형식은 강제.
- **공정 비교 원칙**: 두 모델에 완전히 동일한 프롬프트·원문을 입력. 루브릭은 버전 관리(`rubric_v1`).
- **가중치 분리**: 종합/축 점수는 원점수 + `weights.yaml` 조합으로 조회 시 집계 → 가중치를 바꿔도 원점수 재사용.

## 4. 평가 지표 & 점수 체계

### 4.1 4개 축과 가중치

| 축 | 가중치 | 채점 주체 | 세부 지표(시작점) |
|---|---|---|---|
| **A. 크롤링/접근성** | 30% | 규칙 | robots.txt 허용 여부, sitemap.xml 유무, **llms.txt 유무**, SSR vs JS전용 렌더링, 봇 차단(403/JS월) 여부, 주요 페이지 HTTP 200 도달성 |
| **B. 구조화/시맨틱** | 25% | 규칙 | JSON-LD/Schema.org 존재·타입, 시맨틱 태그 비율, `<title>`·메타·OG 태그 완성도, heading 계층 정합성, alt 텍스트 커버리지 |
| **C. 콘텐츠 품질/완성도** | 30% | **LLM (Claude·GPT)** | 회사가 뭐하는지 명확성, 제품/서비스 설명 충실도, 토크노믹스·백서·팀·컨택 등 핵심정보 유무, 최신성, 모호성/과장 없는 서술 |
| **D. 응답성/기술위생** | 15% | 규칙 | 페이지 로드시간, 모바일 대응, HTTPS/보안헤더, 다국어(한/영) 지원, 깨진 링크 |

> 세부 지표 목록은 시작점이며 `weights.yaml`·루브릭으로 조정 가능. 가중치 30/25/30/15는 시작값으로 확정.

### 4.2 점수 산출 규칙
- 각 지표는 0~100으로 정규화. 축 점수 = 지표 가중평균, 종합점수 = 축 가중평균.
- **규칙 축(A·B·D)**: 크롤러가 결정론적으로 산출 → `model="rule-based"` 단일값.
- **LLM 축(C)**: Claude·GPT 각각 산출 → 모델별 값 + 평균.
- **두 종류의 종합점수가 자연스럽게 도출**:
  - *모델 평균 종합* = A·B·D(규칙) + C(모델평균)
  - *모델별 종합* = A·B·D + C(해당 모델) → Claude 종합 / GPT 종합 분리 뷰에 사용
- **LLM 채점은 근거 텍스트(evidence)를 함께 저장** (왜 이 점수인지 1~2줄) → 개선 항목 도출·상세 표시에 사용.

### 4.3 개선 항목(actionable) 생성
- 각 지표에서 만점 대비 감점된 부분을 "개선 체크리스트"로 자동 변환.
  - 예: "llms.txt 없음 → 추가 권장", "제품 페이지에 JSON-LD 미적용 → 스키마 추가".
- severity(감점 크기·중요도)로 정렬. 우리 회사 상세에서 최상단 강조.

## 5. 데이터 모델 (Supabase / Postgres)

```
companies            분석 대상 기업
  id, name, slug, homepage_url, is_self(우리회사 여부), category, created_at

scans                한 번의 배치 실행(스냅샷)
  id, company_id, scanned_at, rubric_version, raw_snapshot_path, status

metric_scores        지표별 점수 (규칙·모델 통합)
  id, scan_id, axis(A/B/C/D), metric_key,
  model('rule-based' | 'claude-*' | 'gpt-*'),
  score(0~100), evidence(text, LLM 근거), raw_detail(jsonb)

improvements         자동 생성된 개선 항목
  id, scan_id, axis, metric_key, severity, message, suggestion
```

- 종합/축 점수는 `metric_scores`를 가중치로 집계하는 **뷰 또는 조회 시 계산** → 가중치 변경 시 원점수 재사용.
- `is_self=true` 기업은 대시보드 전반에서 "우리 회사"로 하이라이트.
- 규칙·LLM·모델별 점수를 **하나의 `metric_scores` 테이블**에서 `model` 필드로 통일 관리.

## 6. 프로젝트 구조 (모노레포)

```
ai-benchmark/
├─ config/
│   ├─ companies.yaml        # 20~50개 대상 기업 URL·메타
│   ├─ weights.yaml          # 축·지표 가중치 (Methodology 페이지가 이걸 읽음)
│   └─ rubric/rubric_v1.md   # LLM 채점 루브릭 (Claude·GPT 공용)
├─ crawler/                  # 배치 크롤러 (Node/TS)
│   ├─ crawl.ts              # raw/ 로 원문·헤더·렌더결과 수집
│   └─ rule-score.ts         # 규칙 기반 축 A/B/D 채점 → JSON
├─ scoring/
│   ├─ prepare.ts            # LLM 채점 대기목록(원문+루브릭) 표준 입력 생성
│   ├─ claude/…              # Claude Code가 읽고 점수 JSON 출력
│   ├─ codex/…               # Codex CLI가 읽고 점수 JSON 출력
│   └─ import.ts             # 규칙+모델 결과를 Supabase에 적재 (model 태그 부여)
├─ raw/                      # 크롤링 원문 스냅샷 (스캔별)
├─ web/                      # Next.js 대시보드
└─ docs/superpowers/specs/   # 설계 문서
```

### 6.1 LLM 채점 계약 (형식 강제)
- `scoring/prepare.ts`가 기업별로 `{회사, url, 원문텍스트, 루브릭}`을 표준 입력 파일로 생성.
- Claude Code / Codex CLI는 **정해진 JSON 스키마**(축 C 지표별 `score` + `evidence`)로만 출력.
- `import.ts`가 각 출력에 `model` 태그를 붙여 저장.
- → 사람 개입은 "배치를 돌린다"뿐이고, 입출력 형식은 스키마로 강제됨.

## 7. 대시보드 화면 구성

### 화면 1 — 종합 순위 (홈)
- 20~50개 기업 순위표: 종합점수, 4개 축 미니 막대, 모델평균 기준 정렬.
- 상단 **모델 토글** `평균 / Claude / GPT` — 토글 시 종합점수·순위 재정렬.
- **우리 회사 행 고정 하이라이트** + "업계 평균 대비 +/-" 뱃지.
- 축별/카테고리 필터, 검색.

### 화면 2 — 기업 상세
- 헤더: 기업명·URL·종합점수·마지막 스캔일.
- **4개 축 레이더 차트** (모델 평균 + Claude/GPT 오버레이 가능).
- 지표별 점수 테이블: 규칙값 또는 모델별 값 + **LLM 근거(evidence) 펼치기**.
- **개선 체크리스트**: severity 순 정렬, 우리 회사면 최상단 강조.

### 화면 3 — 우리 회사 vs 경쟁사 비교
- 우리 회사 + 선택한 경쟁사 N곳 나란히.
- 지표 히트맵(우리가 지고 있는 항목 빨강), 축별 격차 요약.
- "경쟁사는 되는데 우리는 안 되는 항목" 자동 추출 → 개선 우선순위.

### 화면 4 — 모델 비교 (Claude vs GPT)
- 같은 사이트를 두 모델이 어떻게 다르게 봤나: 지표별 점수 diff.
- 모델 간 편차 큰 항목 하이라이트 (벤치마크 인사이트).

### 화면 5 — 평가 방법론 (Methodology)
- `weights.yaml` + 루브릭을 그대로 읽어 렌더: 축·가중치·지표 정의·채점 주체.
- 루브릭 버전, 채점 모델 버전, 스캔 주기 명시.
- **단일 출처 원칙**: 실제 채점에 쓰인 설정을 그대로 읽어 렌더 → 기준과 표시가 어긋나지 않음.

### 공통
- 반응형, 라이트/다크 지원.
- 점수 색상은 일관된 팔레트(빨강↔초록 스케일).

## 8. 배치 실행 워크플로 (운영)

1. `config/companies.yaml`에 대상 기업 정의/갱신.
2. `crawler/crawl.ts` 실행 → `raw/<scan>/`에 원문·헤더·렌더 결과 저장.
3. `crawler/rule-score.ts` 실행 → 축 A/B/D 규칙 점수 JSON.
4. `scoring/prepare.ts` 실행 → 축 C용 표준 입력 파일 생성.
5. Claude Code 배치 → `scoring/claude/` 점수 JSON 출력.
6. Codex CLI 배치 → `scoring/codex/` 점수 JSON 출력.
7. `scoring/import.ts` 실행 → 규칙·모델별 결과를 Supabase에 적재(`model` 태그).
8. `web/` 대시보드가 저장값을 조회·시각화.
9. 주/월 주기로 2~7 반복 → 새 `scan` 스냅샷 축적(추세 관찰 가능).

## 9. 범위 밖 (YAGNI, 초기 제외)

- 앱 런타임의 온디맨드 실시간 재분석 (초기엔 배치만).
- 앱 내 Claude/OpenAI API 직접 호출 (로컬 배치로 대체).
- 대외 공개/인증·권한 시스템 (내부 사용 우선).
- 100개+ 대규모 산업 지도 (중규모 20~50개 이후 확장 과제).
- 시계열 추세 고급 시각화 (스냅샷은 축적하되 초기 UI는 최신 스캔 중심).

## 10. 열린 항목 (구현 계획에서 확정)

- **기업 리스트 확보**: `companies.yaml`의 실제 20~50개 기업·URL 목록 (사용자 제공 또는 초기 수집 필요).
- GPT(Codex CLI) 배치의 구체적 호출 방식/출력 파일 규약.
- 크롤러의 JS 렌더링 처리 방식(예: headless 브라우저 사용 여부).
- 세부 지표별 정규화 공식(0~100 매핑) 구체화.
